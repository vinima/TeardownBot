# Code guide

How the code is organised and how to make common changes. You don't need to be a programmer to follow this. Each section says which file to open and what to look for.

## The big picture

The app has two halves:

- **The page** (`app/page.tsx`) runs in your browser. It shows the form and displays results.
- **The server** (`app/api/ask/route.ts`) runs on Vercel, or on your computer when you use `yarn dev`. It does the actual work, and it's the only part that knows your API key.

```
Browser (app/page.tsx)
   │  sends { question, urls, password } to /api/ask
   ▼
Server (app/api/ask/route.ts)
   1. Checks the password and the web addresses
   2. Downloads every page at the same time (12-second limit each)
   3. Turns each page into plain text, minus menus ┐
   4. Cuts the text into ~180-word chunks           ├─ lib/retrieve.ts
   5. Fits in 12,000 words? Keep every chunk.       │
      Too long? Keep the best matches (BM25) ───────┘
   6. Sends the numbered chunks + question to the AI model
   ▼
Browser shows answer, cited excerpts, and any pages partly read or failed
```

When the pages are too long to send whole, step 5 picks the relevant text first. This pattern (find relevant text, then have an AI answer from it) is called **RAG**, short for retrieval-augmented generation.

## Files

| File | What it does |
|---|---|
| `app/page.tsx` | The page: the form, preset buttons, suggested questions, results. Also sends analytics events. |
| `app/api/ask/route.ts` | The server endpoint `/api/ask`: checks the input, fetches the pages, retrieves passages, calls the AI. |
| `lib/retrieve.ts` | Plain-text conversion (dropping menus, plus the fallbacks for JavaScript pages and bot checks), chunking, and choosing what the AI reads. Doesn't depend on the web or the AI, so it's easy to test. |
| `lib/retrieve.test.ts` | Automated checks for `lib/retrieve.ts`. Run them with `yarn test`. |
| `app/posthog.tsx` | Starts PostHog analytics and provides `track()` for sending events. Does nothing without a key. |
| `app/layout.tsx` | The HTML shell around every page: browser-tab title, styles, analytics. |
| `app/globals.css` | All styling (colours, spacing, fonts). |
| `package.json` | The app's name, the commands (`yarn dev`, `yarn test`…) and the libraries it uses. |
| `yarn.lock` | The exact library versions. Generated by yarn. Don't edit it by hand. |
| `.nvmrc` | The Node version the app uses (read by nvm). Keep it matching `engines.node` in `package.json`, which Vercel reads. If it goes missing, `scripts/setup.sh` recreates it from `package.json`. |
| `.env.example` | Template for `.env.local`, where your keys go when running locally. |
| `scripts/setup.sh` | One-step local setup (nvm, Node, yarn, libraries, `.env.local`, tests). |
| `scripts/zip.sh` | `yarn zip`: packs the project into `../teardown-bot-<date>-<time>.zip` (a new file each time), skipping everything `.gitignore` lists. |
| `tsconfig.json`, `next-env.d.ts` | TypeScript settings. Rarely need touching. |
| `AGENTS.md`, `CLAUDE.md` | Instructions for AI coding assistants. `AGENTS.md` is written by Next.js itself. |

Folders you'll see after running the app but should ignore: `node_modules/` (downloaded libraries) and `.next/` (build output). Both are recreated automatically and aren't uploaded to GitHub.

## Settings (environment variables)

These are read by the server. Locally they go in `.env.local`. On Vercel they go in **Settings → Environment Variables** (redeploy afterwards).

| Name | Required? | What it does |
|---|---|---|
| `ANTHROPIC_API_KEY` | Yes (or the OpenAI pair) | Uses Claude. Takes priority if both keys are set. |
| `OPENAI_API_KEY` + `MODEL` | Alternative | Uses OpenAI with the named model. |
| `MODEL` | Optional with Anthropic | Overrides the default Claude model (`claude-haiku-5-5`). |
| `APP_PASSWORD` | Optional | If set, the page must send this password. |
| `NEXT_PUBLIC_POSTHOG_KEY` | Optional | Turns on analytics. |
| `NEXT_PUBLIC_POSTHOG_HOST` | Optional | Set to `https://eu.i.posthog.com` for an EU PostHog project. |

Names starting with `NEXT_PUBLIC_` are baked into the page when it's built, so they're visible to anyone. Never put a secret in one. The others stay on the server.

## Common changes and where to make them

| I want to… | File | Look for |
|---|---|---|
| Add or change a preset company button | `app/page.tsx` | `PRESETS` near the top. Add a line like `Stripe: ["https://stripe.com", "https://stripe.com/pricing"],` |
| Change the suggested questions | `app/page.tsx` | `QUESTIONS` |
| Change the page wording (title, intro) | `app/page.tsx` | the text inside `<header>` |
| Change the browser-tab title | `app/layout.tsx` | `metadata` |
| Change colours or fonts | `app/globals.css` | the variables at the top |
| Change how the AI answers (tone, format, rules) | `app/api/ask/route.ts` | the `system:` text inside `generateText` |
| Allow longer answers | `app/api/ask/route.ts` | `Be concise.` in the `system:` text (the length cap, `maxOutputTokens`, also covers the model's thinking, so leave it generous) |
| Allow more pages per question | `app/api/ask/route.ts` | `MAX_URLS` |
| Let the AI read more or less text | `app/api/ask/route.ts` | `CONTEXT_WORDS` (12,000 words ≈ 16,000 tokens) |
| Change chunk size | `lib/retrieve.ts` | `size = 180, overlap = 40` in `chunkText` |
| Use a different Claude model | `.env.local` / Vercel | set `MODEL` (no code change) |
| Track a new analytics event | `app/page.tsx` | call `track("event_name", { ... })` where it happens |

After any change, run `yarn verify`. It runs the tests and a full build, which catches most mistakes before you deploy.

## Details worth knowing

**Retrieval (`lib/retrieve.ts`)**
- `htmlToText` deletes scripts, styles and tags with simple text rules. It's fast and needs nothing extra, but it can't read pages that build their text with JavaScript.
- It also drops menus and footers. When the page marks its main content with `<main>`, it keeps only that (plus the page title), and it removes `<nav>` and `<footer>` sections. On CoreWeave this halved the text without losing content. A trim is used only if at least 30% of the words survive, because some sites put very little inside `<main>` (render.com: 17 of 829 words).
- When a page has fewer than 30 visible words, `fetchPage` (in `app/api/ask/route.ts`) tries two more things, in order:
  1. `isBotCheck` spots the "checking your browser" pages sent by Cloudflare and Vercel, so the app reports "bot check" instead of a misleading "needs JavaScript".
  2. `embeddedText` collects text the page carries for search engines and its own code: the meta description, social-share tags, structured data (JSON-LD) and Next.js's `__NEXT_DATA__`. It keeps only strings that read like sentences, which skips IDs and style names. If that gives at least 10 words, the page is used and reported as **partly read**.

  In testing on about 50 real developer-tool pages, most marketing pages didn't need either step. The failures were mostly bot checks, plus logged-in app screens. For JavaScript pages, the fallback typically recovers one or two sentences, enough for the pitch but not for details. Getting the full text of those pages needs a service that runs a real browser (Jina Reader, Firecrawl, Cloudflare Browser Rendering), which would become a third step.
- `chunkText` makes 180-word chunks. When ranking, they overlap by 40 words so a sentence on a boundary isn't lost.
- `selectChunks` decides what the AI reads, within `CONTEXT_WORDS`:
  - **Everything fits** (most teardowns): every chunk is sent, in page order. This matters because analytical questions ("who is the buyer?") share almost no words with the page. An earlier version always ranked by keywords, and on CoreWeave it found no matches and sent only three navigation menus.
  - **Too much text:** each page's opening chunk goes in first (usually the headline and pitch). The rest of the budget is filled with the chunks that score best on **BM25**, a classic keyword-search formula: a chunk scores higher when it contains the question's rarer words, especially more than once. Common words ("the", "how"…) are ignored. Ties go to chunks nearer the top of their page, so every page gets a share.

**The AI's instructions** (the `system:` text in `app/api/ask/route.ts`) tell it to reason from evidence (who the copy addresses, calls to action, pricing, logos), give a conclusion with a confidence level, cite an excerpt for every fact, and label its interpretation. It should say the pages can't answer only when there's no relevant evidence at all. The answer's citations decide which excerpts the page lists.

**Length limit:** `maxOutputTokens` covers the model's thinking as well as its answer. Claude Haiku thinks before answering by default, so a tight limit can cut the answer off mid-sentence. The response includes `truncated` when that happens, and the page shows a warning.

**Safety (`app/api/ask/route.ts`)**
- `isAllowedUrl` rejects `localhost`, raw IP addresses and internal names, so the server can't be tricked into reading private networks.
- Pages are limited to 2 MB and 12 seconds each. The whole request has 60 seconds on Vercel (`maxDuration`).
- `APP_PASSWORD` stops strangers spending your AI credit. It's a simple shared password, not user accounts.

**The AI call** uses the Vercel AI SDK (`ai` package). `pickModel()` chooses Anthropic or OpenAI based on which key is set, so switching providers needs no code change.

## Tests

`lib/retrieve.test.ts` checks that HTML is cleaned properly, hidden text is found on JavaScript pages (and style names are skipped), bot-check pages are recognised, menus and footers are dropped (with the fallback when `<main>` is nearly empty), chunks are the right size, small inputs are sent whole, and large inputs stay within the budget while keeping each page's opener and the best match. Run them with `yarn test`. It prints `All retrieval tests passed`. A Node warning about "type stripping" is normal.

There are no tests for the page or the server endpoint, so check those by running the app (`yarn dev`) and asking a question.
